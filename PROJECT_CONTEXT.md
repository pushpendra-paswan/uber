# PROJECT_CONTEXT.md

Living status file for the Uber-like ride-hailing learning project. Claude Code reads this at the start of every session and updates it after every milestone. Milestone definitions live in `CLAUDE.md`.

## Project summary

Uber-like ride-hailing web app for learning. FastAPI + PostgreSQL/PostGIS + Redis backend with layered structure (routers, services, repositories), plain HTML/CSS/JS frontend (rider, driver, admin), simulated drivers, no ML layer.

## What exists now

- **Services (Docker Compose):** `db` (postgis/postgis:16-3.4, volume `postgres_data`, port 5432), `redis` (redis:7-alpine, port 6379), `osrm` (`ghcr.io/project-osrm/osrm-backend:v26.10.0-debian`, `osrm-routed --algorithm mld /data/city.osrm`, data mounted read-only from `./osrm/data`, published on `127.0.0.1:5000` for debugging only, no healthcheck), `backend` (FastAPI, port 8000, `uvicorn --reload --ws-max-size 65536`; the Dockerfile CMD has the same flag; since M4.2 it also publishes `127.0.0.1:8001` for a SECOND uvicorn process started by hand, see "How to run and test"). Backend waits for db and redis to be healthy. It does not wait for osrm: with OSRM down the API starts and routing answers 502. The `osrm` container exits with an error until `osrm/prepare.sh` has been run
- **Tables** (migrations `0001_initial_schema`, `0002_unique_vehicle_per_driver`, the data-only `0003_seed_economy_pricing_rule`, `0004_ride_offers`, and `0005_safety_net_unique_indexes` (M4.3, indexes only, no data change); ids are integer PKs, all `created_at` are timestamptz default `now()`, money is integer paise):
  - `users`: role (rider/driver/admin), name, email (unique), phone (unique, nullable), password_hash
  - `drivers`: user_id (FK users, unique), license_number, verification_status (pending/approved/rejected, default pending)
  - `vehicles`: driver_id (FK drivers, unique `uq_vehicles_driver_id`: one vehicle per driver), plate_number (unique, stored normalized: uppercase, no spaces or hyphens), model, color, vehicle_type (default economy)
  - `rides`: rider_id (FK users), driver_id (FK drivers, nullable), pickup/dropoff lat, lng, address, status (default REQUESTED), distance_m, duration_s, fare_estimate, final_fare, otp, started_at, completed_at. Indexed: status, rider_id, driver_id. `otp` (String(4), nullable) is the trip code: `1234` from DRIVER_ASSIGNED until the trip starts, NULL again once the ride is IN_PROGRESS or CANCELLED (M3.5, no migration: the column already existed) **M4.3 indexes:** `uq_rides_one_active_per_driver` (unique on driver_id WHERE status IN DRIVER_ASSIGNED, DRIVER_ARRIVED, IN_PROGRESS) and `uq_rides_one_active_per_rider` (unique on rider_id WHERE status IN REQUESTED, DRIVER_ASSIGNED, DRIVER_ARRIVED, IN_PROGRESS); the conditions are plain strings because the enum values are stored as upper-case names (checked in psql).
  - `ride_events`: ride_id (FK, indexed), from_status (nullable), to_status, actor_user_id (FK users, nullable)
  - `ride_offers` (M3.3, migration `0004`): ride_id (FK rides), driver_id (FK drivers, indexed `ix_ride_offers_driver_id`), status (PENDING/ACCEPTED/REJECTED/EXPIRED/CANCELLED, default PENDING, stored as VARCHAR(9) with the enum NAME, which equals the value), pickup_distance_m (int, straight line from the driver to the pickup when the offer was made), created_at, expires_at (timestamptz, the deadline, compared with the backend clock), responded_at (timestamptz, set only for ACCEPTED and REJECTED). Constraints: unique `uq_ride_offers_ride_id_driver_id` (a driver is never offered a ride twice), partial unique index `uq_ride_offers_one_pending_per_ride` on (ride_id) `WHERE status = 'PENDING'` (one open offer per ride), index `ix_ride_offers_status_expires_at` on (status, expires_at) (the sweeper's query). No ORM relationships. Constants (top of `services/matching.py`): `OFFER_TIMEOUT_SECONDS = 15`, `MAX_OFFERS_PER_RIDE = 5` (next to `SEARCH_RADIUS_M = 3000` and `MAX_CANDIDATES = 50`) **M4.3 index:** `uq_ride_offers_one_pending_per_driver` (unique on driver_id WHERE status = 'PENDING'; it also counts a PENDING offer past its deadline that is not yet swept, because `now()` cannot be in an index condition). All three are declared in `models.py` with `postgresql_where`, so the test database gets them from `create_all` too.

  - `ratings`: ride_id, from_user_id, to_user_id (FKs), score (check 1 to 5), comment. Unique (ride_id, from_user_id)
  - `pricing_rules`: vehicle_type (unique), base_fare, per_km, per_min, min_fare, surge_cap (float, default 2.0). One row seeded by migration 0003 (all money in paise): `economy`, base_fare 5000 (Rs 50), per_km 1200 (Rs 12), per_min 200 (Rs 2), min_fare 8000 (Rs 80), surge_cap 2.0. The test database gets the same row after every truncate

Driver queries eager load with `selectinload`; ride events are never loaded through the ride, only via `rides_repo.list_events`. Enums are Python enums in `models.py` (`UserRole`, `VerificationStatus`, `RideStatus`, `OfferStatus`, `PaymentMethod`, `PaymentStatus`), plus the constant `ACTIVE_RIDE_STATUSES` (REQUESTED, DRIVER_ASSIGNED, DRIVER_ARRIVED, IN_PROGRESS)

Declared before the `/rides/{ride_id}` routes. Nothing is stored
  - `POST /rides`: role rider; JSON `{pickup_lat, pickup_lng, pickup_address, dropoff_lat, dropoff_lng, dropoff_address}` (any other field the client sends is ignored). In ONE transaction (committed once) it creates the ride as REQUESTED with its first event, makes the first offer to the nearest free driver (`matching.offer_to_next_driver`), and, if nobody qualifies, moves the ride to NO_DRIVER_FOUND. Two outcomes, both HTTP 201 with `RideResponse`: status `REQUESTED` with `driver_id` null (an offer is pending and offers are being tried; no driver is assigned until one accepts), or status `NO_DRIVER_FOUND` with `driver_id` null (nobody in range or free; a normal finished ride, not an error; the rider can request again at once). After the commit it publishes `offer_created` to the offered driver. Errors: 409 `You already have an active ride` (checked first, so no routing or Redis call is made, and checked AGAIN after the rider's row is locked, see "Concurrency control"); 503 `Busy, please retry` when the rider's row stays locked by another request for more than 3 s (`LOCK_WAIT_MS`); the same 422, 502, and 503 errors as the estimate; 503 `Cache is unavailable` if Redis fails during matching; 422 for out-of-range coordinates, blank address, or identical pickup and drop-off. A failure anywhere before the commit leaves no ride, no event, and no offer behind. The server works out the estimate itself and stores `distance_m`, `duration_s`, and `fare_estimate` on the ride (the path is not stored)

The pickup and drop-off names equal `RideResponse` on purpose. No rider name, email, phone, or id

Go online first.` (no presence key); 503 `Busy, please retry` when the driver's row stays locked for more than 3 s (M4.2). Nothing is changed on a refusal. After the commit it publishes `ride_updated` to the rider and `offer_closed` (reason `accepted`) to the driver
  - `POST /offers/{offer_id}/reject` (M3.3): role driver; 204 with no body. Same 404 and the same two 409s as accept. The offer becomes REJECTED (`responded_at` set) and `finish_offer` offers the ride to the next driver, or ends it as NO_DRIVER_FOUND (null actor) when there is none
  - `GET /rides/active`: role rider or driver; their active ride, or 404 `No active ride`; 403 for admin. Declared before `/rides/{ride_id}`
  - `GET /rides/{ride_id}` and `GET /rides/{ride_id}/events`: any logged-in user who is the ride's rider, its assigned driver, or an admin. Everyone else, and unknown ids, get the same 404 `Ride not found`
  - `GET /rides/{ride_id}/driver` (M3.2): any logged-in user who is the ride's rider, its assigned driver, or an admin (everyone else and unknown ids get `404 Ride not found`, no token gets 401); 404 `No driver assigned to this ride` when `driver_id` is null. 200 `RideDriverResponse`: `driver_id, name, vehicle (id, plate_number, model, color, vehicle_type, or null), location (lat, lng, updated_at, or null)`, and nothing else: no email, phone, license number, or verification status. `location` comes from Redis (`get_presence`) ONLY while the ride is in `ACTIVE_RIDE_STATUSES`; for COMPLETED and CANCELLED it is always null even if the driver is online for another ride, and a missing or expired presence is null as well. 503 `Cache is unavailable` when Redis is down, although name and vehicle come from Postgres
  - `POST /rides/{ride_id}/arrive`, `/start`, `/complete`: role driver (403 otherwise), must be the assigned driver (404 otherwise); 200 `RideResponse`; 409 `Cannot change ride from X to Y` if the transition is not allowed. `/start` sets `started_at` (and now needs the trip code, next item); `/complete` sets `completed_at` and leaves `final_fare` null. Since M3.5 each of them also sends `ride_updated` to both people (see the WebSocket events)
  - `POST /rides/{ride_id}/start` (M3.5): JSON body `{"otp": "<4 digits>"}` (`StartTripRequest`, pattern `^[0-9]{4}$`: no body, a missing field, a number, `"12"`, `"abcd"`, `"12345"`, and full-width digits all give 422). The STATE is checked first: a ride that is not DRIVER_ARRIVED gives 409 whatever the code. On a DRIVER_ARRIVED ride a wrong code, or a ride with no stored code, gives 400 `Incorrect trip code` with no status change, no event row, and nothing published (the comparison is `secrets.compare_digest`). The right code moves the ride to IN_PROGRESS

The ride's own rider gets 200 `{"otp": "1234"}` while the ride is DRIVER_ASSIGNED or DRIVER_ARRIVED; another rider and an unknown id get 404 `Ride not found`; every other status (REQUESTED, IN_PROGRESS, COMPLETED, CANCELLED, NO_DRIVER_FOUND) gives 409 `Trip code is not available`. The only place the code leaves the backend

Since M3.3, if the ride has a PENDING offer it is set to CANCELLED in the same transaction (ride locked first) and the offered driver gets `offer_closed` (reason `ride_cancelled`) after the commit. - **Ride state machine** (`ALLOWED_TRANSITIONS` and `change_ride_status()` in `services/rides.py`; the only code that sets `ride.status` after creation, apart from `create_ride`, which inserts REQUESTED and writes the first event with `from_status` null):

  | From | Allowed to |
  |---|---|
  | REQUESTED | DRIVER_ASSIGNED, CANCELLED, NO_DRIVER_FOUND |
  | DRIVER_ASSIGNED | DRIVER_ARRIVED, CANCELLED |
  | DRIVER_ARRIVED | IN_PROGRESS, CANCELLED |
  | IN_PROGRESS | COMPLETED |
  | COMPLETED, CANCELLED, NO_DRIVER_FOUND | nothing |

  Every transition loads the ride with `SELECT ... FOR UPDATE`, writes a `ride_events` row, and commits once. The table did not change in M3.3, but the meaning did: REQUESTED now means "offers are being tried", and DRIVER_ASSIGNED happens only when a driver accepts an offer (actor = that driver's user id). The system's own change is REQUESTED to NO_DRIVER_FOUND (actor null), made by `create_ride` (nobody qualifies for the first offer) and by `finish_offer` (no next driver after a reject or expiry); there is no endpoint for it. `change_ride_status` takes `actor_user_id: int | None` (type hint only; the logic is unchanged). **Trip code (M3.5):** `change_ride_status` sets `ride.otp = FAKE_OTP` (`"1234"`, a constant at the top of `services/rides.py`; a real system would use `secrets` for random digits) when the ride becomes DRIVER_ASSIGNED and sets it to NULL when the ride becomes IN_PROGRESS or CANCELLED; nothing else changes the field and `ALLOWED_TRANSITIONS` is unchanged. Only the ride's rider can read it (`GET /rides/{id}/otp`) and it never appears in `RideResponse`, ride events, WebSocket events, or logs. `driver_set_status(db, user, ride_id, new_status, otp=None)` checks the code (state first, then code), changes the status, commits, and then calls `notify_ride_updated(db, ride)`, the private helper that `cancel` also calls: it publishes `ride_updated` `{ride_id, status}` to the rider's user id and, when `ride.driver_id` is set, to the driver's user id (looked up with one extra scalar query, `drivers_repo.get_user_id`).
- **Matching and offers (M2.4, reworked in M3.3):** `services/matching.py` has one function, `offer_to_next_driver(db, ride)` (since M4.2 it also locks the chosen driver, see "Concurrency control"; it replaced `find_driver`, which was inlined into it because it now has one caller). It reads the drivers already offered this ride (`offers_repo.list_driver_ids_for_ride`, any status); at `MAX_OFFERS_PER_RIDE` (5) or more it returns None. Otherwise: `GEOSEARCH` around the PICKUP (`SEARCH_RADIUS_M = 3000`, `MAX_CANDIDATES = 50`, nearest first, with distances), presence keys with one `MGET` and `ZREM` of stale GEO members (as in M2.4), `get_available_ids` (approved, no ride in `ACTIVE_RIDE_STATUSES`, and no PENDING offer: a driver deciding on an offer is busy), minus the drivers already offered this ride; since M4.2 the candidates are sorted by `(distance_m, driver_id)` and tried in that order: `drivers_repo.try_lock` (skip when the row is locked), then `get_available_ids(db, [driver_id])` again as its own statement (skip when unavailable), then it creates the PENDING offer for the first driver that passed both (`pickup_distance_m` rounded from the GEOSEARCH distance, `expires_at` = backend now + 15 s) and returns it. It never changes the ride, never publishes, never commits. The candidate list is recomputed for every offer from live presence and availability, not fixed when the ride is requested. `repositories/drivers.py` has `search_nearby`, `get_online_ids`, `remove_from_geo`, `get_available_ids`, and (M3.3) `get_user_id(db, driver_id)` (events are addressed to user ids). `repositories/drivers.py` also has `try_lock` and `lock` (M4.2)
- **Offers (M3.3):** `repositories/offers.py` (Postgres only, flush but never commit, no rules): `create`, `get_ride_and_driver_ids` (selects ONLY the two columns: the locked read of the entity that follows must be its first load in the session, or the identity map would return an older unlocked copy and the status check under the lock would be stale; I chose columns-only over `populate_existing`), `get_by_id(db, id, for_update)`, `list_driver_ids_for_ride`, `get_pending_for_ride`, `get_oldest_pending_for_driver(db, driver_id, now)`, `list_due(db, now, limit)` (columns `id, ride_id` of PENDING offers with `expires_at <= now`, ordered by `expires_at`), `set_status(db, offer, status, responded_at=None)`. `services/offers.py`: `get_pending`, `accept`, `reject`, `finish_offer`, `expire_due_offers`, `sweep_forever`, with `OFFER_SWEEP_INTERVAL_SECONDS = 1` and `DUE_BATCH_SIZE = 50`. LOCK ORDER everywhere (accept, reject, expiry, cancel): the RIDE row first (`FOR UPDATE`), then the OFFER row (and, since M4.2, accept takes the DRIVER row third). `finish_offer(db, ride, offer, new_status, reason)` is the one private helper (used by reject and expiry): sets REJECTED/EXPIRED (`responded_at` only for REJECTED), calls `offer_to_next_driver`, moves the ride to NO_DRIVER_FOUND (null actor) if there is no next offer, commits, and then publishes `offer_closed` to this offer's driver and either `offer_created` to the next driver or `ride_updated` (NO_DRIVER_FOUND) to the rider. Events are published AFTER the commit. One INFO log line per offer event (created, accepted, rejected, expired, cancelled) with offer, ride, and driver ids, and one when a ride ends as NO_DRIVER_FOUND after offers. `sweep_forever()` is one asyncio task per backend process (started and cancelled in the `lifespan` next to the WebSocket listener): every `OFFER_SWEEP_INTERVAL_SECONDS` it calls `expire_due_offers()`, which opens its own sessions through `database.async_session` (looked up at call time, so tests replace it): one session lists up to 50 due offers, then a NEW session per offer locks the ride, loads the offer `FOR UPDATE`, skips it unless it is still PENDING and still overdue, and calls `finish_offer(..., EXPIRED, "expired")`. An exception aborts the pass (the first failure stops it); `sweep_forever` logs ONE warning when a failure streak starts and ONE info line when it recovers, and keeps looping. State is in Postgres, so a restart loses nothing, and several processes can sweep at once (the ride lock makes the second one see a non-PENDING offer and skip). `events.publish` is now best-effort: it catches `RedisError`, logs one warning with the event type and user id, and returns 0, so a failed publish never fails or undoes a request that already committed (nothing in the code or tests relied on it raising)

    | none (404) | wander to a random point | next wander leg on the next tick |
    | DRIVER_ASSIGNED | route to the pickup | `POST /rides/{id}/arrive` |
    | DRIVER_ARRIVED | stay put | after 2 ticks, `POST /rides/{id}/start` with `{"otp": <--otp>}` |
    | IN_PROGRESS | route to the drop-off | `POST /rides/{id}/complete` |

    A 409 from arrive, start, or complete is ignored (the next tick resyncs). A 400 from start (wrong code, M3.5) is logged ONCE per ride as `action: wrong trip code for ride N` (the same text every tick, so the existing change-only logging prints it once, then `action recovered` when the ride is gone) and retried on the next tick (at most one try per tick); a 422 is logged once like any other unexpected answer. A ride that disappears (rider cancelled) is dropped and the driver wanders on. Ping answers: 200 ok; 409 means presence expired, so `POST /drivers/me/online` with the current position; 401 means log in again and retry once; 403 means rejected, log it and stop that driver only; 422, 502, 503, network errors, and timeouts are a failed ping and the driver keeps going. At most one retry per tick.
  - **Output:** `logging` with timestamps (httpx's own request log is silenced). Only changes are logged: online (and how), ride assigned with the straight-line distance to the pickup, arrived, trip started, trip completed, ride gone, a problem when it starts (once per kind and text, such as `ping: ping answered 503`) and `... recovered`. Every 15 s one summary line: `running R/N, on a ride X, pings ok A failed B, avg ping M ms, rides completed C` (interval values, except rides completed). Ctrl+C (a signal handler on POSIX; on Windows asyncio.run cancels the main task instead, which the code handles but was not run on Windows) stops the drivers, sends `POST /drivers/me/offline` for each (a 409 for a driver on a ride is ignored; its presence just expires), prints a `final:` line, and exits within about half a second for 50 drivers.

Movement matched speed x factor within 2 percent over 15 s; 20 samples of one driver were at most 0.2 m from the nearest road; all start points were 0.8 to 4.7 km from the center (limit 5); a 30 driver fleet at 90 km/h completes a 2.7 km trip in about 2.5 minutes including the approach; the matched driver was always the nearest from `GEOSEARCH`.
- **Concurrency control (M4.2):** Postgres row locks, `FOR UPDATE`, one mechanism, no switch. Three critical sections, each = lock, then the deciding check as its OWN statement, then the write, then the commit (which releases the lock): **C1** `create_ride` locks the rider's `users` row (`users_repo.lock`) after `estimate_ride` (so never across OSRM) and re-runs `get_active_for_rider`; the first check stays as the cheap early exit that costs no routing call. **C2** `matching.offer_to_next_driver` keeps the prefilter (`get_available_ids` over all candidates; stale is fine, it only avoids useless locks), then walks the candidates in `(distance, driver id)` order: `drivers_repo.try_lock` (`FOR UPDATE SKIP LOCKED`; a locked driver is SKIPPED, never waited for), then `get_available_ids(db, [driver_id])` again; the first driver that passes both gets the offer. It is also used by `finish_offer`, so reject and expiry are covered. **C3** `offers.accept` takes `drivers_repo.lock` (blocking `FOR UPDATE` on the driver row) after the existing ride and offer locks and BEFORE the status, expiry, approved, active-ride, and presence checks. All lock queries are column-only selects (`select(Driver.id)`, `select(User.id)`), so the identity map cannot return a stale entity. `users.lock` and `drivers.lock` first run `SET LOCAL lock_timeout = <database.LOCK_WAIT_MS>` (3000, an `int()` formatted into the statement, read at call time so tests can patch it). When that expires SQLAlchemy raises `sqlalchemy.exc.DBAPIError` with `error.orig.sqlstate == "55P03"` (the cause is `asyncpg.exceptions.LockNotAvailableError`); the service wraps ONLY the lock call in `try/except DBAPIError`, re-raises anything that is not 55P03, and answers **503 `Busy, please retry`**. There is no 409 for lock contention any more. The timeout stays set for the rest of the transaction. **Lock order:** blocking locks only as ride row, offer row, driver row (accept), or the rider's user row alone (create_ride); every lock taken while another is held in matching is non-blocking (SKIP LOCKED), so no cycle can form. Verified: 0 `deadlock detected` lines in the Postgres log over the whole session (every stress run, including two processes, and every test run). Tests widen the race window with `widen()` (see Tests); production code has no delay. The race itself and the evidence are in "Known races" and "Fix and compare results".
- **Safety net (M4.3):** the three partial unique indexes above are the last line of defense behind the locks. Each place that can hit one catches `sqlalchemy.exc.IntegrityError` narrowly: `create_ride` wraps the ride creation through the commit (rollback, 409 "You already have an active ride"); `matching.offer_to_next_driver` wraps the offer insert in a savepoint (`db.begin_nested()`), catches the error outside it, logs WARNING `offer skipped for driver <id>: <error text>`, and tries the next candidate (the transaction and the request survive); `accept` wraps everything from the first change through the commit (rollback, 409 "You already have an active ride"). With the locks working none of these ever fires (see "Edge cases" for the numbers), so an `offer skipped` warning means a lock failed. `get_available_ids` excludes a driver with ANY pending offer (live or overdue), which is what the pending-offer index counts.
- **Offers sweeper (M4.3):** `expire_due_offers` reads ALL PENDING offers (`offers_repo.list_pending(db, 200)`, oldest `expires_at` first, replaces `list_due`), makes ONE `drivers_repo.get_online_ids` call for their drivers (never with an empty list), and treats an offer as due when its deadline has passed (reason `expired`) or else when its driver has no presence key (reason `driver_offline`: the driver went offline, an admin rejected them, or their page died and the key expired). Each due offer gets a NEW session: lock the ride, load the offer under its lock, skip it unless it is still PENDING and still due (for `driver_offline` presence is re-checked), then `finish_offer(..., EXPIRED, reason)` (`responded_at` stays null). Outage errors (`OUTAGE_ERRORS` = `RedisError`, `OSError`, `sqlalchemy.exc.InterfaceError`, `sqlalchemy.exc.OperationalError`) abort the whole pass, and `sweep_forever` logs the streak once; any other exception logs ONE warning per offer id (`Offer sweeper could not handle offer N`) and the pass goes on (module-level set `failed_offer_ids`, pruned to the still-pending ids at the start of each pass). Provoked classes when Postgres stopped: `InterfaceError` ("connection is closed", a dead pooled connection) and `socket.gaierror` (an `OSError`, the host `db` unresolvable); during the few seconds of shutdown a plain `DBAPIError` ("the database system is shutting down") also appeared, which is handled as a per-offer failure (one warning per offer, the next pass recovers). Offer closed reasons on `offer_closed`: accepted, rejected, expired, ride_cancelled, driver_offline.

      |---|---|

      | 4400 bad message | Report `"closed"`. Only the Reconnect button resumes (our client never sends a bad message, so this is a bug) |
      | any other code (1000, 1001, 1006, 1011, 1012, 4408, ...), a connection that fails to open, or a watchdog timeout (reported as code 4000, our own) | Retry with backoff |
      | `disconnect()` was called | Nothing, ever |

    - **Backoff:** equal jitter. Before the n-th retry (n from 0) `cap = min(30000, 1000 * 2^n)` and `delay = cap / 2 + random * cap / 2`: 0.5 to 1 s, 1 to 2, 2 to 4, 4 to 8, 8 to 16, then 15 to 30 s. The counter returns to 0 only when a connection had been authenticated for at least 10 s before it was lost, or on `reconnectNow()`; a server that accepts and then drops us keeps escalating the backoff.

After `auth_ok` a heartbeat sends `{"type":"ping","data":{}}` every 20 s and arms the watchdog with 8 s unless one is already running, so a dead connection is found within 28 s. Any frame received clears it (before `auth_ok` only `auth_ok` does; the server sends nothing else then). When it fires the old socket is detached (all four handlers set to null) and `close()` is called inside a try/catch, and the loss is handled at once as code 4000, without waiting for the browser's close event (a half-dead connection can take minutes to report one). Every handler of a socket first checks it is still the current one. FOR UPDATE; SELECT pg_sleep(600);` in `psql -c`): the driver was skipped (NO_DRIVER_FOUND) the whole time, and killing the psql CLIENT with `kill -9` did NOT release the lock: the server backend stayed `active / PgSleep` and the driver was still unmatchable 31 s later (and for the full 600 s if left), because Postgres does not notice a dead client while a query is running (`client_connection_check_interval` is 0, `pg_sleep` never reads the socket). This was different from the expectation in the plan ("almost at once"). **Postgres, a holder idle in its transaction** (what a crashed app process looks like when it dies while awaiting OSRM, Redis, or a timer: the server is waiting for the next statement): killing the client released the lock at once, the very next request matched the driver (0.0 s later). Settings in this database: `idle_in_transaction_session_timeout` = 0 (disabled), `lock_timeout` = 0 (the app sets 3 s per transaction), `client_connection_check_interval` = 0. If the holder HANGS instead of crashing: in Redis the lock expires by itself after 10 s while the holder is still alive, so the protection silently ends and the holder's late write can duplicate (that is F2); in Postgres the lock lasts as long as the holder's transaction, so matching skips that driver (and accept or `POST /rides` for that driver or rider answer 503 after 3 s) until the transaction ends, the server kills the session, or an admin does; nothing becomes inconsistent, the cost is availability of that one driver or rider. `idle_in_transaction_session_timeout` is the setting that would bound it (not set; out of scope).
- **Failure experiment F2: the lock expires while held (redis only, ARTIFICIAL).** Both Redis TTLs set to 100 ms, delay 300 ms, `--scenario drivers --rounds 10`: **I1 violated in 7 of 10 rounds** (2 offers on one driver, 39 offers against 30 expected), I2 0 of 10, and the log had **269 `lock expired before release` warnings**. The same delay 300 ms in mode postgres: **0 violations in 10 rounds**, 30 of 30 offers, no 503, median `POST /rides` 703 ms (the redis F2 run: 706 ms). The TTL constants and the delay were then reverted (the saved copy of `locks.py` was identical, and the file was deleted with the loser).
- **Logs.** `docker compose logs db | grep -ci "deadlock detected"` = 0 over the whole session (every run of every mode and every test run). A per-mode pass (delay 50, drivers x20 and riders x10 per mode, backend logs saved before the next recreate) found, for none, redis, and postgres: 0 deadlocks, 0 `lock expired before release`, 0 tracebacks, 0 HTTP 500, 0 HTTP 503. The 15 `canceling statement due to lock timeout` lines in the Postgres log are all expected: 2 per test run (test 8) and 1 from the probe that found the exception class.
- **Rubric, in order.** (1) Invariants: both mechanisms 0 violations in every run (8 of 8 each, F2 excluded). (2) Lost matches: both 0 (offers exactly 60 of 60, 30 of 30). (3) 5xx and deadlocks: both 0. (4) F1 and F2: redis can leave a free driver unmatchable for up to 10 s after a holder crash and loses correctness when a lock expires inside its critical section (no fencing); postgres releases at once when the holder dies idle, keeps the lock when the holder dies mid-query, and never loses correctness when the holder is slow. (5) Code and places that must remember to release: redis about 50 added production lines (a 21-line `repositories/locks.py`, about 23 lines in the three services, a `held_locks` parameter on `offer_to_next_driver`) and 4 places that must release (three `finally` blocks in `create_ride`, `accept`, and `finish_offer`, plus the early release when the re-check says unavailable); postgres about 30 added production lines (the `git diff --stat` of the final code is 75 insertions and 11 deletions in six backend files, comments included) and 0 places to release (commit and rollback do it). (6) Latency, medians of `POST /rides` redis vs postgres: 424 vs 438 ms (a), 594 vs 625 (b), 1345 vs 1374 (c), 478 vs 510 (d), 429 vs 447 (e), 624 vs 673 (f), 273 vs 280 (g), 453 vs 514 (h): postgres is 2 to 14 percent slower at the median here and the maxima are within the noise of one development machine.
- **Decision: Postgres row locks win.** Both are correct on the first three criteria (and the lost-match count shows the "skip a busy driver" rule works in both), so the tie-break from the plan applies: fewer added lines and fewer failure modes. Postgres adds about 30 lines against about 50, nothing to release by hand (a commit, a rollback, or a dead connection does it, so a forgotten `finally` cannot leak a lock), no TTL to tune against the length of the critical section (the Redis lock is only as safe as 10 s is longer than the slowest request, and F2 shows what happens otherwise), and a lock that lives in the same transaction as the data it protects, so it holds across any number of backend processes without more machinery (verified with two). What it costs: a request can hold a database connection for up to 3 s while it waits, the answer to contention is 503 instead of a fast 409, and a holder stuck mid-query keeps its lock (F1). Redis' one real advantage, failing fast without taking a connection, is not needed here: matching never waits, and the waiting calls are rare (one rider, one driver). The Redis path, the `none` path, the switch (`CONCURRENCY_MODE`, `EXPERIMENT_DELAY_MS`), the three delay spots, and `repositories/locks.py` were deleted.

| M4.3 | `IntegrityError` is caught only at the three places that can hit an index (`create_ride`, the offer insert in matching, `accept`), each narrowly and with a rollback; the answer is 409 or a skipped candidate, never a 500 | A global exception handler; catching in the repositories | Services own the use case and the commit, so they know what to undo and what to say; nothing broader is caught, in line with "minimal error handling" |
| M4.3 | A vanished driver's offer is withdrawn by the sweeper through the presence key, one rule for three causes (explicit offline, admin rejection, which already removes presence, and presence expiring because the page died) | Closing offers inside `go_offline` and `set_verification`; a separate cleanup for page death | One rule covers every cause, including ones no endpoint sees; `go_offline` and `set_verification` stay unchanged. The price is up to about a second before the offer closes, and one MGET per pass |
| M4.3 | Time expiry wins over `driver_offline` when both apply (reason `expired`) | The other way round | The deadline is the stronger fact (the driver had the whole window); it keeps the old reason for old behavior. The check order in the sweeper is deadline first |
| M4.3 | Duplicate accept stays a 409, not idempotent | Returning the existing ride with 200 for the same driver | The 409 tells the client the offer is gone and its refresh shows the ride; an idempotent accept needs a decision about who may replay, which is not needed yet |
| M4.3 | The sweeper isolates each offer: any ordinary exception is logged once per offer id and the pass continues; outage errors (`RedisError`, `OSError`, `InterfaceError`, `OperationalError`) still abort the pass and `sweep_forever` logs the streak once | Catching everything; catching nothing (the M3.3 behavior, one bad offer blocked the rest) | One broken offer must not starve the offers behind it, but an outage means every offer would fail, so stopping and retrying next second is right. The log set is module-level and pruned to the still-pending ids each pass, so a permanently failing offer logs once, not every second |
| M4.3 | The sweeper reads ALL pending offers (limit 200) and makes one MGET, instead of only the late ones | A per-driver presence lookup; reading only late offers and adding a second query for the rest | One SELECT and one MGET per second whatever the number of drivers. Measured under the heavy chaos load: median 2.7 ms and 0.6 ms |
| M4.3 | The chaos scenario uses probabilistic agents (fixed seed, per-agent `random.Random`), a settle period, and a precise definition of STUCK: after the settle period any REQUESTED ride or PENDING offer. Rides left assigned, arrived, or in progress when the agents stop are not stuck | Scripted interleavings; counting every unfinished ride | Random agents find interleavings nobody wrote a test for, and the seed makes a run repeatable in its choices (not its timing). A ride whose driver simply stopped is a legitimate state (see the open issues); a REQUESTED ride with nobody deciding is exactly what the sweeper must prevent. Drivers stop pinging at the deadline, so their presence dies after 30 s and the sweeper clears the rest, which is why the settle default is 45 s |
| M4.3 | I5 to I7 (overdue pending offers, pending offers on a ride that is not REQUESTED, assigned rides without an ACCEPTED offer for their own driver) count at ANY snapshot | Allowing a short grace period | Each pair of changes is one transaction (accept sets the offer and the ride together, every offer closing is in the ride's transaction), so none of the three can be legitimately violated even for an instant. I5 is the exception with a margin of 10 s: it detects a slow or dead sweeper, and a sweep interval of 1 s plus a pass is far below that |

Timing is not repeatable: `--seed` fixes the agents' choices, not the interleaving. Most chaos rides end at once as NO_DRIVER_FOUND (supply), so only about one request in five gets an offer.
- **M4.3: `MAX_CANDIDATES` (50) can still hide a free driver behind busy ones** (unchanged from M4.2 and M3.3; the GEO search returns the 50 nearest members before the availability filter).
- **M4.3: the hung (not crashed) lock holder from M4.2 is still open.** A request stuck mid-query keeps its driver or rider row locked; matching skips that driver and accept or `POST /rides` answer 503 after 3 s. The new indexes do not change that. `idle_in_transaction_session_timeout` would bound it (not set).
- **M4.3: the browser click-through was not run** (no browser tool was available in the session). The backend behavior behind it was checked by tests, WebSocket events, and curl; the driver page text for `driver_offline` is one string in `driver.js` and was only checked by reading the served file. To do by hand: (1) driver tab online, rider requests, the driver clicks Go offline: within about 2 s the offer panel closes with "The offer was withdrawn because you went offline."; (2) request again with an offer showing, reject the driver in the admin tab: the same notice within about 2 s and the driver tab shows the rejected message; (3) with a second driver tab online the offer moves to it within about 2 s and the rider tab still says "Looking for a driver"; (4) the normal flow, countdown, tracking, and reconnect still work.
- **M4.3: a connection refused or a name-resolution failure is an `OSError`,** so the sweeper treats every `OSError` as an outage and aborts the pass. A plain `DBAPIError` ("the database system is shutting down") during a Postgres shutdown is NOT in that list and is logged as a per-offer failure for a few seconds. Acceptable; widen `OUTAGE_ERRORS` if it becomes noisy.
